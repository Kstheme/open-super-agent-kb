# openkb

**一个单机可跑、可长期维护的知识库。资料变了，它告诉你哪些产物需要修订。**

[English](./README.md)

openkb 首先面向**制度与合规清单维护**。给它一批制度文件和一个目标，Agent 从原文提取带证据的声明，用它们组装清单或报告。每条声明都能追溯到原文的具体版本和位置。制度更新后，openkb 找出受影响的声明和产物条目，提出修订建议，由你确认。

**示例**　用差旅制度生成一份报销审核清单。住宿限额调整后，openkb 会指出清单中受影响的审核项，附上新条款和建议改法。你可以对照证据确认这次修订。

## 为什么

传统企业知识库有四个可预期的失败：

| 失败 | 典型做法 | openkb |
|---|---|---|
| 检索就是终点 | 返回片段，结论自己拼 | 直接交付产物（清单、报告）并附证据 |
| 答案不可追 | 引用"某文档"，版本丢失 | 每条声明指向具体版本的具体位置 |
| 知识会腐坏 | 靠人记得去改 | 源头变更 → 受影响声明 → 只复核这部分 |
| 使用有门槛 | 建目录、打标签、维护分类 | 用自然语言说目标 |

## 差异在哪

1. **按目标交付产物。** 系统按产物骨架计算缺口，Agent 围绕缺口查找证据，组装成可用的清单或报告。
2. **每条声明都能追溯到原文。** 例如，清单中的审核项可以回查到 2024 年 6 月版制度的第 2.3 节。
3. **按受影响条目复核。** 资料更新后，系统定位可能受影响的声明，Agent 判断变化是否构成实质影响，并为相关产物条目提出修订建议。

## 怎么做的

- 资料按结构切块并算出跨版本稳定的块键，Agent 抽取声明，每条必须绑定 span。**没有 span 就不入账**，账本会拒绝。
- 依赖不单独存表。"哪些声明依赖这份文档"由 `证据 → 块 → 版本 → 文档` 反查得出，因此永远不会与证据不一致。
- 文件 hash 变化时，系统算出受影响集合，Agent 判断是否**实质影响**。系统管记账，Agent 管判断。
- 任务可恢复：每步检查点，副作用走持久队列；预算到顶不是抛异常，而是留下可续跑的任务和缺口清单。

## 检索

默认 hybrid：FTS5（中文用 trigram）+ 向量，RRF 融合，再重排。重排默认开——这个场景要的是"少而准"，不是"多而全"。向量扩展加载失败时降级为 FTS5 + numpy 精确检索，不会直接不可用。

## 后端

| 后端 | 依赖 | 状态 |
|---|---|---|
| SQLite + sqlite-vec | 无（pipx 即可） | v0.1 默认 |
| SQLite 纯 FTS5 | 无 | v0.1 降级，自动切换 |
| Postgres + pgvector | 自备 PG 16+ 与 pgvector | roadmap |
| Milvus | — | 不做，见 [rejected](./docs/rejected.md) |

## 模型

只支持 OpenAI 兼容协议。配 `base_url` 和 key 即可，OpenAI、DeepSeek、vLLM、Ollama 都能用。结构化输出走 JSON Schema 校验加重试，不依赖各家 function calling。Embedding 默认走同一 endpoint，`openkb init` 时可切换本地 `sentence-transformers`。

## 数据

全部在 `~/.openkb/`：

```
kb.db          # 账本、任务、产物（单文件）
originals/     # 原始资料，保留每个版本
config.toml
```

备份是复制目录，迁移也是复制目录。

## 状态

项目处于 **pre-alpha**。M4 可使用 pipx 安装已构建的本地 Web 应用。按 [M4 业务级手动验收](./docs/m4-manual-acceptance.md) 安装，并用独立的 Section 508 演示包验证从资料导入到清单复核和历史回查的流程。 [系统设计](./docs/design.md) · [M0 评测规范](./docs/specs/0001-m0-eval-harness.md)

## 不做什么

不做账号、多租户、网页抓取、自动应用修订、多 Agent 互聊。每一条拒绝都带理由记在 [docs/rejected.md](./docs/rejected.md)。
