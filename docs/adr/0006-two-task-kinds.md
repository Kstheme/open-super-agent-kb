# 建库与委托是两类任务，预算与恢复粒度不同

F1 要求 100 份 docx/pdf 建库。按每份几十个块、每块一次抽取调用算，这是几千次模型调用；而单任务预算是 40 步 / 15 万 token / 10 分钟。沿用同一套预算，建库在数学上不可能完成。

两者的失败语义也相反：委托超限时 `paused` + 缺口清单是有意义的（用户看到"还缺什么"）；建库超限时 `paused` 对用户只是"卡住了"。

决定：`task.kind` 分两类。`ingest` 的预算按文件计，checkpoint 粒度是"一个文件完成即落盘"，失败进失败清单（F1 已定义），**没有缺口概念**。`deliver` 与 `review` 沿用 40 步 / 15 万 token / 10 分钟。

## Considered Options

- **提高全局预算**：委托任务失去成本护栏，用户不敢点，与"成本可见，用户才敢随便点"直接冲突。
- **把建库拆成 N 个委托任务**：用户要手工分批，进度不可见，且续跑靠人记。
- **建库不设预算**：首次建库账单不可控，这是最容易被投诉的那一类账单。
- **建库也用缺口清单**：用户看不懂"建库还缺什么"。缺口的语义是"目标未被覆盖"，不是"文件还没处理"。

## Consequences

- 状态机多一个 `kind` 分支：预算、checkpoint 粒度、进度呈现各自不同。
- `ingest` 的暂停是正常可恢复的中间态；`deliver` / `review` 的 `paused` 是例外路径。
- 建库成本单独计量并展示，与委托成本分开。否则"一次问答多少钱"会被首次建库摊薄成噪声。
- F7 的"带缺口清单继续"只适用于 `deliver` / `review`；`ingest` 的续跑是"从下一个未完成文件继续"。
