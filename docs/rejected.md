# 不做什么

这不是路线图，是边界。每条都记录理由和"什么时候可以重新考虑"，避免同一条讨论反复发生。

## 产品层

### 账号、权限、多租户

单用户本地优先，不做登录、成员、角色。写入带 `actor`（恒为 `local`），为将来留位。

**重新考虑的条件**：出现真实的多人协作诉求（不是"以后可能"），且已有稳定的单人链路。

### 自动应用修订

复核产生的差异提案必须由人按块确认。

**理由**：一次错改就会让用户永久关闭这个功能。信任是不可逆资源。

### 通用域支持

v0.1 只有一个声明模板（制度/合规）。换域 = 换模板，不换内核。

**理由**：通用域无法评测，只能说"能跑"，不能说"做得好"。

## 技术层

### Postgres + pgvector

见 [ADR-0001](./adr/0001-sqlite-only-with-store-port.md)。核心冲突：pgvector 需要外部 Postgres 实例，违反 pipx 一条命令的承诺；若上 PG，账本必须一并迁移，成本是双份仓储层与测试矩阵。

**重新考虑的条件**：单库超过约 50 万块，或出现明确的"只能用 PG"的部署诉求。

### Milvus

两套向量库需要双写，必然出现一侧未写入的瞬间；且 Milvus 面向千万到亿级分布式场景，与单人语料规模不匹配。

**重新考虑的条件**：基本不存在。真到这个规模，项目定位已经变了。

### 多 Agent 互聊

不做多个 Agent 互相发言、互相点评的编排。

**理由**：任何一轮产出必须改动至少一个持久对象，否则删掉。参考 BettaFish 的主持人机制——发言但不改变下游状态，成本高、无杠杆。

### 网页抓取与第三方同步

v0.1 只接本地目录。

**理由**：演示只需要"文件变了"；抓取引入合规、反爬与稳定性负债。

### 独立规范治理

`spec/` 跟随代码演进，不设 RFC 流程与治理委员会。

**重新考虑的条件**：出现第二个独立实现，且愿意共同维护 schema。

### 不依赖各家 SDK 做结构化输出

只用 OpenAI 兼容协议 + JSON Schema 校验重试。

**理由**：各家 function calling 行为不一致，行为不可预测比少支持几家更贵。
