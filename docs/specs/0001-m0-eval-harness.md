# M0：评测 harness

对应 [design.md](../design.md) §12 与里程碑 M0。

## Problem Statement

仓库现在只有设计文档，没有一行代码。整条技术路线的价值押在一个"必须打败的对手"上：资料变更后，用同一模型、同一检索索引把产物整体重新生成一遍，再做语义 diff。但没人知道这个对手能得多少分、花多少钱。

因此维护者现在无法回答四个问题：

1. **差异点是否成立。** "资料变了知道该改哪"是这个项目唯一的差异。在拿到对手的同口径分数之前，无法判断它比"重新生成 + diff"强在哪，强多少。
2. **成本是否可接受。** 一次复核花多少 token、多少钱，直接决定用户"敢不敢随便点"。没有基线，任何成本承诺都是猜的。
3. **进展是否可衡量。** 后续每个里程碑都需要一条可回退的对照线。现在没有，等于每步都在裸奔。
4. **是否值得被相信。** 外部审阅者的第一个问题永远是"你怎么知道它有用"。没有可复现的公开评测，这个问题只能靠嘴回答。

更麻烦的是：这四个问题不能等到核心写完再回答。core 一旦成型，就会被沉没成本绑架，评测也从"判定"退化成"背书"。所以顺序必须是先建评测。

## Solution

一个可复现的评测 harness。它把"资料变更后产出差异提案"抽象成一个端口，让任意实现接进来跑同一套 gold set，输出四个指标并按需比对。

对外形态是两条命令：

```
openkb eval run     --goldset <path> --system <name> --runs 3 --out report.json
openkb eval compare --report-a <a.json> --report-b <b.json>
```

跑完得到两份东西：一份带版本号的 JSON 报告（可入库、可 diff、可长期跟踪），一段人读摘要（本次用了哪个模型、哪个 gold set 版本、哪个声明模板版本、判定阈值是多少、结论是什么）。

**M0 的交付重点是量出对手的分数，不是证明本方赢。** 默认情况下"我方"是一个零提案的空实现，harness 照样跑出完整的四个指标——这是设计文档明确允许的起点（"哪怕本方是空的"）。真正要在 M0 结束时拿到的数字是：对手的召回率、误报率、时延、成本各是多少。预置的判定规则是：对手召回率接近且成本更低，则账本方案降级为"只提供定位"。

gold set 随仓库公开，语料是小规模合成中文制度文件（条款编号、含表格），配 5 次修订与逐条人工标注。它既是评测输入，也是项目对外"可复现"承诺的实物。

## User Stories

1. 作为维护者，我想要一条命令跑完全套评测，这样我不必记一串脚本顺序就能拿到结论。
2. 作为维护者，我想要默认的"我方"实现是零提案的空实现，这样 harness 的管路正确性可以和"我们的算法有多好"分开验证。
3. 作为维护者，我想要在不写任何核心代码的前提下先拿到对手的四个指标，这样 M0 能否通过不取决于 core 的进度。
4. 作为维护者，我想要每次运行的报告都记录模型 id、gold set 内容哈希、声明模板版本、价格表版本，这样三个月后我能确认两个数字是不是可比。
5. 作为维护者，我想要同一份 gold set 连跑多次并看到每次之间的分歧率，这样我知道指标的波动是模型不稳定还是真实退步。
6. 作为维护者，我想要指标计算是纯函数并被独立测试，这样我不用怀疑"分数是算法算出来的还是 harness 算错的"。
7. 作为维护者，我想要一个"完美系统"的测试替身，它必须拿到满分；拿不到就说明 harness 有 bug，这样我能用一条断言给整个度量链上保险。
8. 作为维护者，我想要一个"永远判实质影响"的测试替身，它的召回率和误报率都可以手算出来，这样我能用固定数值锁住指标定义。
9. 作为维护者，我想要受影响条目召回率按案例计算再取平均，而不是把全语料混成一个池子，这样一个只有单条受影响条目的案例不会被大案例吃掉。
10. 作为维护者，我想要误报率的分母包含"无实质影响"和"完全未受影响"两类条目，这样系统"多报以求全"的策略会被显式惩罚。
11. 作为维护者，我想要时延分成"总墙钟时间"和"模型耗时"两个数，这样我能看出慢在模型还是在 harness。
12. 作为维护者，我想要成本同时给出 token 数和估算金额，且价格未知时明确记为空值而不是猜一个数，这样报告不会因为一个臆造的价格而失真。
13. 作为维护者，我想要"每次正确找出一个受影响条目要花多少钱"这个派生指标，这样我能直接比较两条路线的性价比，而不是只比总花费。
14. 作为维护者，我想要预算超限或运行时抛错的案例被计为漏检并单独列出，而不是从统计里消失，这样失败不会伪装成"这个案例不存在"。
15. 作为维护者，我想要报告里有一份缺口清单（paused 任务缺什么），这样"没跑完"和"跑完了但没找对"能被区分。
16. 作为维护者，我想要对手实现拿到的输入与真实使用者拿到的一致（语料 + 既有产物 + 目标），这样它的分数才有说服力。
17. 作为维护者，我想要对手在小语料上可以直接读完整语料，并把这个简化写进报告，这样我清楚这个偏差是对我不利的方向。
18. 作为维护者，我想要系统实现必须显式声明是否读过账本，这样"我方偷偷用了对手看不到的信息"这类作弊会在报告里暴露。
19. 作为维护者，我想要判定阈值写在配置里并在报告中回显，这样一次"结论"能被复核，而不是藏在某个常量里。
20. 作为维护者，我想要 gold set 的标签在加载时被严格校验（条目 id 必须存在于产物、修订对必须自洽、不得重复标注），这样标注错误会在跑之前失败而不是污染指标。
21. 作为制度/合规域的标注者，我想要 gold set 用条款编号的合成制度文件而不是随意段落，这样"块级对齐"和"受影响"的判断贴近真实场景。
22. 作为制度/合规域的标注者，我想要每个案例除了"是否受影响"还能写"应该改成什么"和"依据哪一段"，这样复核质量不只看命中，还能看改得对不对。
23. 作为制度/合规域的标注者，我想要 gold set 里包含只改措辞、不改语义的修订，这样误报率才有真实的分母。
24. 作为制度/合规域的标注者，我想要 gold set 里包含一个完全没变的对照案例，这样我能确认系统在无变更时不会凭空产生提案。
25. 作为贡献者，我想要新增一个被评测系统只需实现一个端口，这样我不必理解 harness 内部就能提交自己的方案。
26. 作为贡献者，我想要新增一个 gold set 案例只需按固定格式加文件并通过校验，这样评测集能长期长大而不需要改代码。
27. 作为贡献者，我想要 harness 在模型端点不可达时立即失败并给出明确原因，这样我不会把网络错误误读成"系统表现差"。
28. 作为贡献者，我想要两份报告可以并排比对并高亮每个指标的差值，这样我能回答"我这版改动是不是真的更好"。
29. 作为审阅者，我想要把评测结果和新加的案例一起跑通，这样我能验证作者的数字而不是只能相信它。
30. 作为审阅者，我想要 harness 不依赖任何私有数据或外部服务（除模型端点外），这样我在自己机器上能复现同一组数字。
31. 作为审阅者，我想要报告里明确写清"这是 M0，我方是空实现"，这样我不会把对手的基线误读成项目的能力。
32. 作为未来的用户，我想要在 M0 就看到真实成本数量级，这样我能在投入资料之前判断这个工具对我是否划算。

## Implementation Decisions

### 唯一测试缝：复核系统端口

M0 只引入一条缝：**被测复核系统的端口**。它是 harness 与所有实现之间的唯一契约，也是全部端到端测试的落点。

```
ReviewSystem.review(ReviewRequest) -> ReviewResult
```

`ReviewRequest` 携带：

- `corpus`：变更前与变更后两版资料，按 `document → version → block` 组织；block 带 `block_key`、`heading_path`、`ordinal`、`start_offset`、`end_offset`、`text`。沿用设计文档 §7 的资料侧结构，即使 M0 还不落库。`block_key` 在 M0 不参与任何计算，但必须出现——数据形状与 M1 一致，否则类型改造会推迟到最贵的时刻（ADR-0005）。
- `artifact`：基线产物，条目带**稳定 `item_id`** 与 `snapshot_text`。`item_id` 跨版本不变，是逐条比较的前提。
- `goal`：产物要满足的目标（用户当初的委托）。
- `budget`：步数、token、墙钟上限。
- `ledger`：**可选**账本视图。对手可以不读；我方可以读。

`ReviewResult` 携带：

- `proposals`：逐条提案，每条为 `item_id` + 判定（`material` / `immaterial` / 不涉及）+ 可选修订文本 + 可选证据引用。
- `cost`：输入/输出 token、估算金额、模型 id。
- `timing`：模型耗时与总耗时。
- `state`：`done` / `paused` / `failed`，paused/failed 附带缺口清单或错误原因。
- `used_ledger`：是否读取过账本。

`used_ledger` 是刻意的自我审计字段。它让"我方比对手多拿了信息"这件事无法隐藏，也让将来的报告读者能判断比较是否公平。

### 三个实现

1. **`noop`（默认）**：返回零提案。这不是占位符，是 M0 的正式基线——它证明 harness 在"什么都没有"的情况下仍产出完整四个指标。
2. **`regenerate`（对手）**：读变更后语料与目标，按基线产物的章节结构整体重新生成产物，再在条目层做语义对齐与 diff，对变化的条目提提案。它必须遵守同样的预算上限。
3. **`oracle`（仅测试）**：直接读 gold 标签。它不进产物、只在测试里作为校准器存在，防止 harness 被当成一个自带作弊后门的工具发布。

### 指标定义

四个指标必须给出精确口径，否则 M0 的结论不可用。

- **受影响条目召回率**：`|判 material 且 gold 为 material| / |gold 为 material|`。
- **误报率**：`|判 material 且 gold 不为 material| / |gold 不为 material|`，分母同时包含"有意改成无实质影响"和"完全未受影响"两类条目。
- **时延**：从变更触发到可审阅差异落盘。输出总墙钟与模型耗时两个数，见上文故事 11。
- **成本**：token 与估算金额；派生"每正确找出一条受影响条目的成本"。

所有比例指标**先按案例计算，再跨案例取算术平均**（宏平均）。`--runs N` 时报告每次运行的值、中位数，以及逐案例的判定分歧率。分母为零的案例在报告中标记为"不适用"，不参与该指标的聚合，并在摘要里列出被排除的案例——不静默丢样本。

### 失败不消失

抛错、超预算、模型返回不可解析的响应，一律计入 `failed` / `paused`，在召回率里按漏检计，同时单独列出。缺口清单原样保留。这条规则来自设计文档 §10："超限不是抛异常，而是留下可续跑的任务和缺口清单。"

### 偏向自己不利的简化

小语料下，对手可以直接把全部资料读进上下文，而真实场景里它只能用检索结果。这会让对手显得比实际更强。**保留这个简化**，并在报告里注明。理由：偏差朝"对我方不利"的方向偏，若对手在有利条件下仍然不够便宜或不够准，结论就更站得住；反之，如果我方在不利设定下都赢了，那个胜利才可信。

同理，M0 默认不给"我方"任何手写账本。要不要为每个案例预置一份复核过的账本，是在 M1 建库之后才能诚实回答的问题；M0 用 `noop` 明确表示"还没量"。

### gold set

- 小规模合成中文制度语料，条款编号，含表格，便于块级对齐。
- 5 个修订案例 + 1 个"完全未变"对照案例。
- 20–30 条声明级标注，逐条标 `material` / `immaterial` / `not_affected`，material 的附"应改成什么"与"依据哪一段"。
- 每条标注同时记录该产物条目**引用了哪几条声明、哪几段证据**。M0 不用它，但 M2 之后评"产物有没有挂对证据"要复用这套 gold set；事后再补等于重造一份标注。
- 每个案例是一个自洽的修订对（变更前语料、变更后语料、基线产物、标注），随仓库提交，用内容哈希做版本号。
- 加载即校验：条目 id 必须属于基线产物、修订对两侧自洽、同一 `item_id` 不得重复标注、标注必须覆盖产物的每一条。校验失败在跑之前报错。

### 报告与判定

- 报告为带版本号的 JSON，包含 `harness_version`、`goldset_hash`、`system`、`model_id`、`profile_version`、`price_table_version`，以及逐案例、聚合两层指标。
- 判定阈值（如"召回率接近"的容差、"更便宜"的比例）写在配置里，在报告与摘要中回显实际取值。摘要给出的结论标注为**建议性**，最终取舍仍由人决定——与设计文档"实质影响由 Agent 判断，人不接受自动裁定"的立场一致。
- `compare` 只做差值呈现，不做自动裁决。

### 配置与失败模式

模型端点、key、价格表来自 `~/.openkb/config.toml`（沿用设计文档 §11 的数据目录）。配置缺失或端点不可达时**立即失败并说明原因**，不做静默降级——把网络故障算进"系统表现"是这类评测最常见的脏数据来源。

## Testing Decisions

好的测试只断言外部可观察行为：给定 gold set 与某个复核系统实现，报告里的数字应该是什么。测试不关心 harness 内部怎么遍历案例、怎么拼 prompt。

- **指标计算是纯函数，用表驱动测试**。手算期望值覆盖：全对（满分）、全判 material、零提案、只有 `immaterial` 的案例、分母为零的案例、`--runs` 下三次结果不一致的案例。
- **端到端测试走唯一那条缝**：用 `noop`、`oracle`、以及一个"永远判 material"的替身各跑一遍，断言报告 JSON 中的聚合指标。`oracle` 必须满分——这是整个度量链的自检。
- **gold set 校验器单独测试**：条目 id 不在产物里、修订对不自洽、重复标注、漏标，各自必须报错。
- **失败计入漏检**：用一个故意抛错的替身，断言该案例出现在失败清单里且计入漏检，而不是被跳过。
- **成本与时延**：用记账型替身（返回固定 token 数）断言成本聚合；时延只断言"总耗时 ≥ 模型耗时"这类必然关系，不断言具体毫秒数。
- **不测**：具体 prompt 文本、报告 JSON 的字段顺序、摘要的措辞。

仓库目前没有任何测试，因此没有既有先例可参照。第一批测试同时确立本项目的测试风格：**测试朝向端口，替身替代外部依赖，断言可观察结果**。模型客户端按既有架构约束本就只出现在 `agent/` 层，它是已有边界，不算为 M0 新开的缝。

## Out of Scope

- 真正的账本、`Store` 端口、SQLite 与任何 migration。
- 资料导入管线、docx/pdf 解析、结构感知切块的工程实现（M0 的合成语料直接以块结构提交）。
- 检索：FTS5、向量、RRF、rerank 全不做；对手在小语料上整读即可。
- 任何界面：无 Web、无 CLI 以外的交互、无差异确认 UI。
- 文件 watcher 与 `openkb sync`。
- 真实用户资料与任何私有数据。
- 自动应用修订、多 Agent 编排、Postgres 与 pgvector。
- 多人协作、账号、权限。

## Further Notes

- **M0 的成功标准不是"我们赢了"**，而是"四个指标在两条路线上都可复现地跑出来，且对手的分数已经明确"。若对手召回率高、成本更低，按设计文档收缩为"只提供定位"，这个结论本身即是 M0 的合格产出。
- **合成语料的质量就是评测的天花板。** 若条款切分在真实 docx/pdf 上不成立，M0 的高分会在 M1 立刻失效。因此合成语料要刻意包含表格与跨条款引用这两个最容易出问题的形态。
- **`item_id` 的稳定性是整件事的地基。** 它一旦不稳，逐条比较就退化成整篇语义 diff，对手和我方也就无从比较。设计文档 §7 的 `artifact_claim.snapshot_text` 正是为此存在。
- `oracle` 只存在于测试中。发布出去的 harness 不应带一个能读答案的实现，哪怕它被 flag 关掉——那会永久削弱这份评测的可信度。
- **gold set 的两个前向兼容点**：`block_key` 与"标注附带声明/证据引用"。它们不让 M0 多测任何东西，只是避免 M2 之后为评测产物而重造标注、重改类型。这是本轮唯一刻意超出 M0 范围的设计，理由是成本接近零而返工成本是几天。
- 本文放在 `docs/specs/`，与设计文档 §5 的 `spec/`（账本结构、事件、schema）分开。前者描述一次工作，后者是对外版本化的数据契约，两者演进节奏不同。
