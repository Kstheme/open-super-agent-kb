# M1：账本与跨领域建库

依据 [系统设计](../design.md#13-里程碑)、[ADR-0001](../adr/0001-sqlite-only-with-store-port.md)、[ADR-0005](../adr/0005-block-identity-and-alignment.md) 和 [ADR-0006](../adr/0006-two-task-kinds.md)。

## Problem Statement

用户需要把一批本地资料建成可核验的账本。实际资料包含 Word 表格、跨页 PDF 和 Markdown。同一份资料更新后，未修改的段落可能换了页或位置。用户要能确认哪些块仍然对应，并从证据回到它所依据的那一版原文。批量建库还需要能承受单个文件失败和处理中断，否则一次问题就可能迫使用户重跑整批。

M0 已通过手动验收。M0 的合成制度案例直接给出资料块，尚未验证真实文档的解析、版本管理和证据回点。

## Solution

提供一条本地建库链路，导入原生 DOCX、可选取文本的 PDF 和 Markdown，保留原文版本，按结构切块，并允许从证据查到对应版本的原文位置。法规和技术文档共用入库与回点流程。自动声明抽取和入账沿用制度合规声明模板。

先从公开资料确认可下载、可复用的原文件和真实版本对，再验证块稳定键。通过稳定键门槛后，验收 100 份 DOCX/PDF 建库、按文件恢复和 12 条证据回点。

## User Stories

1. 作为建库用户，我希望指定一个本地目录，以便一次导入一批资料。
2. 作为建库用户，我希望直接使用原生 DOCX，以便保留原来的标题、段落和表格。
3. 作为建库用户，我希望导入带文本层的 PDF，以便按原页核验资料。
4. 作为建库用户，我希望导入 Markdown，以便技术文档的标题、列表和代码块能保留结构。
5. 作为建库用户，我希望扫描 PDF 明确提示定位受限，以便知道哪些资料需要另行处理。
6. 作为资料维护者，我希望同一资料的新旧版本都保留，以便后来能复查当时的原文。
7. 作为资料维护者，我希望重复导入相同内容不重复建库，以便安全地重跑目录。
8. 作为资料维护者，我希望插入无关段落后仍能认出原有块，以便变更范围不会随位置漂移。
9. 作为资料维护者，我希望新插入的段落被单独识别，以便区分新增内容和原有内容。
10. 作为资料维护者，我希望没有条款编号的技术文档也能对齐，以便两类资料都能维护版本。
11. 作为资料维护者，我希望无法确认的对应关系明确列出，以便人工检查歧义。
12. 作为评测维护者，我希望知道每份公开资料的地址、版本、许可和文件哈希，以便复用同一批输入。
13. 作为评测维护者，我希望受控插入与真实版本对分别报告，以便区分位置漂移和实际修订带来的问题。
14. 作为建库用户，我希望看到完成数量和失败清单，以便掌握批量进度。
15. 作为建库用户，我希望中断后从未完成文件继续，以便保留已完成的工作。
16. 作为建库用户，我希望看到失败文件名和失败原因，以便快速定位输入问题。
17. 作为建库用户，我希望换掉坏文件后只重试它，以便避免重跑全批。
18. 作为制度合规使用者，我希望自动提取的声明附有可核验的原文片段，以便相信已入账的内容。
19. 作为账本审阅者，我希望从声明的证据回到正确资料、版本和位置，以便核对原文。
20. 作为账本审阅者，我希望证据能精确定位到 Word 表格行，以便确认是哪条规则支持声明。
21. 作为账本审阅者，我希望证据能定位到 PDF 指定页，以便在多页资料中复查。
22. 作为账本审阅者，我希望新版移动段落后旧证据仍指向旧版原文，以便历史记录保持可追溯。
23. 作为技术文档审阅者，我希望用人工标注的证据验证回点，以便直接检查定位质量。
24. 作为评测维护者，我希望有一套固定的 100 份验收清单，以便复现建库规模和恢复结果。

## Implementation Decisions

- 单机本地使用。持久数据通过 `Store` 端口访问，首个实现为 SQLite。保留资料身份、原文版本、资料块、声明、证据和建库任务。相同资料内容的重复导入保持幂等。
- 块稳定键遵循 ADR-0005，使用归一化标题路径、可用的条款编号和归一化文本哈希。块序号只用于排序，位置偏移用于原文定位。表格按行切块，合并单元格适用单独的处理规则。定位受限的扫描资料遵循 ADR-0005 的整份资料降级规则，并显式报告限制。
- 保留归一化规则和哈希口径的版本信息，并在块稳定键验收报告中回显。无法确认的跨版本对应关系显式列出，供人核验。
- 证据绑定到具体资料版本中的块和原文片段。原文版本独立保存，后续导入或移动段落时仍能复查旧证据。制度合规自动抽取继续遵守有可校验原文片段才入账的规则。
- 建库任务按文件计量预算，每完成一个文件记录可恢复进度。中断或预算耗尽从未完成文件继续。失败清单记录文件和原因，支持针对单文件重试。建库任务不使用委托与复核任务的缺口语义。
- 首批候选为 [GovInfo 法规历史年版](https://www.govinfo.gov/help/cfr) 的原生 PDF、[Kubernetes 中文文档](https://github.com/kubernetes/website/tree/main/content/zh-cn/docs) 的 Markdown 修订，以及 [Section508.gov 原生 DOCX](https://www.section508.gov/create/documents/)。先核对具体文件的原始下载地址、可用版本、复用许可和文件哈希，再冻结验收清单。

## Testing Decisions

- **主要测试缝**是用户可操作的本地建库入口和它返回的可观察结果。测试从资料原文件发起导入、恢复或重试，并通过本地验收入口查阅资料版本、块对齐结果和证据。优先沿用已有本地 CLI 作为入口。命令名与参数由实现工单细化。
- **块稳定键门槛先于后续建库验收。** 法规与技术文档各做受控无关插入，由人工预先标出未改动的原有块。用「稳定键一致且正确一对一对应的未改动块数 ÷ 人工标出的未改动块总数」计分。要求 100% 一致、零错配，插入段另验为新增。
- **真实版本对单独验收。** 用公开资料的真实历史版本，人工预标可确认的对应块。要求零静默错配，无法确认的对应关系明确列出。报告实际一致率。首批固定样本要求 PDF 正文条款标题 6/6、Markdown 正文锚点 5/5。
- **100 份建库验收。** 固定 100 份不同的原生 DOCX/PDF，两种格式各至少 10 份，要求全部成功入库。重复文件、同一资料的不同版本以及 Markdown 单独记录。Markdown 用于跨领域验证。
- **恢复与重试验收。** 在第 51 份处理中断，重启后从第 51 份继续。前 50 份不重复处理，最终 100 份均成功。另用一份坏文件验收失败清单，替换后只重试该文件。
- **证据回点验收。** 预先标注 12 条证据，DOCX、PDF 和 Markdown 各 4 条，全部回到正确资料、版本和位置。必须包含 DOCX 表格行、PDF 指定页和新版移动段落后仍能回看旧版原文。技术文档可以使用人工标注的证据。
- **测试风格。** 验证可观察的入库结果、完成进度、失败原因和原文位置。沿用 M0 CLI 测试以真实文件和报告核对行为的方式，以及固定模型替身确保自动测试可以离线重跑的做法。业务手动验收用真实资料，制度合规的自动声明入账用真实模型另行核查。

## Out of Scope

- 跨领域自动声明抽取和产物交付。技术文档在 M1 验收到可入库、可对齐、可回点。
- 完整委托、产物骨架填充和产物交付属于 M2；变更复核和差异提案属于 M3。
- 扫描 PDF 的 OCR、完整 Web 审阅界面、网页抓取与第三方同步。
- 多用户权限和非 SQLite 存储实现。

## Further Notes

- 首批固定样本及真实版本验收门槛已在 #13 核验并确认。
- 100 份的验收衡量批量建库和恢复。跨版本对齐准确性和原文回点各用单独的人工标注样本验收。
